The design question

You want two distinct endpoints:

  1. payrollMonth for employees
  2. payrollMonth for project-leads

First question worth sitting with: where does this concept belong in the hexagon?

The employee variant's logic is: "has this employee completed their ControlTimes monthend task for the previous month?" That's pure monthend domain knowledge — the computation depends on monthend task state.

But the consumer of this endpoint is the frontend loading the worktime view. So there's a tension:

monthend knows the answer (task completion)
worktime is the context the frontend is navigating into

Three options on the table:

A) Add to the worktime context — WorkTimeEmployeeResource and WorkTimeProjectLeadResource each gain a GET /worktime/employee/payroll-month endpoint. The employee resource needs an outbound port to query monthend completion, which creates a cross-context dependency (worktime → monthend).

B) Add to the monthend context — MonthEndResource (or dedicated sub-resources) exposes the payrollMonth endpoints. Makes sense because the logic lives there, but it's conceptually odd to ask monthend "what month should I show worktime for?".

C) Add to shared — A new cross-cutting resource like PayrollMonthResource. No business logic leaks either direction. The employee logic gets its own use case that reaches into monthend state via an outbound port.

Thread 1: What is the project-lead rule?
